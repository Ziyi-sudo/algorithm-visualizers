左边没有哨兵，右边有 —— 同样删一个节点，看谁会崩

哨兵不是装饰，它是一个「永远不会被删掉的假节点」。
有了它，真实节点的 prev 和 next 永远不可能是 null —— 所以那些 null 判断就都不需要了。

哨兵是什么



  
一个不装真实数据的假节点，永远待在链表里，永远不会被删除。288 那份答案里它的 ch 是 null，就是明摆着说"我不是真字符"。

  
它唯一的作用是站在边界上，替真实节点挡住 null。原本"第一个节点的 prev 是 null"这种边界情况，现在变成"第一个节点的 prev 是哨兵" —— 边界消失了，所有节点长得一样。

  
代价是多一个对象。收益是 remove 从四个 if 变成一个。





为什么 288 还要「循环」



  
只有一个哨兵放在头部的话，头这边被兜住了，但尾巴那边还是 null：

  
[哨兵] ⇄ [a] ⇄ [b] → null —— 删 b 时 b.next.prev 就是 null.prev，照样崩。

  
288 的做法是让最后一个的 next 指回哨兵，形成环 —— 这样一个哨兵就同时兜住了两头。append 里那句 node.next = head 就是在维持这个环，漏了它环就断了，remove 立刻 NPE。

  
另一种常见做法是头尾各放一个哨兵，不用环。效果一样，代价是多一个对象。





三种方案对比



  

    
方案remove 里判断要额外维护什么

    
不用哨兵（你的 205）四个 if无，但每个边界都要自己想清楚

    
一个哨兵 + 循环（288）一个 ifnode.next = head 维持环

    
头尾两个哨兵一个 if多一个对象，最好写

  

  
三种都对，只是把复杂度放在了不同地方。不用哨兵是"代码里到处判"，用哨兵是"结构上一次性堵死"。
