整个方法只靠一个移项

  

    若「某祖先之后 → 当前节点」这一段的和 = target

    则　prefixSum[当前] − prefixSum[某祖先] = target

    移项　prefixSum[某祖先] = prefixSum[当前] − target
  

  
站在任何一个点，prefixSum[当前] 和 target 都是已知的，所以要找的那个祖先前缀也就算得出来。剩下的问题只有一个：这样的祖先真的存在吗？把路上见过的所有前缀和丢进 Set，一次 contains 就查完了。

  
注意「算出来」和「找到」是两回事。prevSum − target 只是一张通缉令——它描述了要找的祖先长什么样，但那个祖先存不存在，得去 Set 里查。


  
为什么 Set 里要先放一个 0

  
0 代表「还没走任何一步」的空前缀。有了它，起点恰好是 root 的路径才匹配得上——否则 5 → 11 → 6 这种从头开始的整条路会被漏掉。


  
Set 里装的只是当前这条链

  
进门放进去，出门要拿掉。任何时刻 Set 的内容都等于「从 root 到当前节点」这一条链上的前缀和，大小是 O(height) 而不是 O(n)。不删的话，走到右子树时会看到左子树留下的前缀，而它们根本不在同一条向下的链上。

  
螺丝刀原理：prefixSums.add(x) 返回 false 说明这个值早就有人放进去了（两个祖先的前缀和撞了）。那它不是你的，走的时候别删——所以要用 needRemove 记一下。是你拿过来的你带走，不是你放的别动人家的。


  
和 Method 1 的差别

  
Method 1 站在每个点往回扫一遍所有祖先，O(n × height)，最坏 O(n²)。Method 2 把那个循环换成一次 Set 查询，降到 O(n)。思路来自数组题「找和为 target 的 subarray」——一条 root→leaf 的路就是一个数组。


  
为什么这题只能 top down

  
它要问的是「我头上的祖先里有没有某个前缀和」。祖先的信息只能从上面带下来，子树 return 上来的东西里没有祖先。所以和 639 / 140 那种两个方向都能写的题不同，这题锁死 top down。
