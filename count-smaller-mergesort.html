276 · Get Count Array

排序时顺手把人数记下来

归并排序里，右半边每被取走一个，就说明它比左边剩下的所有人都小。所以当左半的某个元素终于被放下时，「已经从右半取走了几个」就是它右边比它小的个数——r - mid - 1。排序是幌子，计数才是目的。

数据组

原数组 A（永远不动，只被查值）

helper —— 本次 merge 开始前 indexArray 的快照（蓝＝左半　橙＝右半）

indexArray —— 正在被写回（按 A 的值排序，但装的是下标）

countArray —— 答案，只增不减

为什么排序能顺手算出答案

第一件事：排的是下标，不是值

indexArray 里装的是原下标 0 .. n-1，比较大小时才去查 array[下标]。

为什么必须这样：答案 countArray[i] 要按原位置存。如果直接把值排序，元素一动就不知道它原来是第几个了，答案没处放。要保住位置信息，就存下标。（678 / 204 / 198 都撞过这条判据。）

第二件事：那条撑住一切的不变式

在任何一次 merge 里：

  indexArray[left .. mid]     里的每一个原下标
        全都 <
  indexArray[mid+1 .. right]  里的每一个原下标

为什么成立：归并排序是按位置区间分治的。区间 [left,mid] 从头到尾只装原下标在 [left,mid] 里的元素，右半同理。归并只在区间内部重排，永远不跨区间搬人。

所以「右半的元素」和「原数组里在我右边」是同一件事。 这就是为什么数右半取走的个数，等于数「右边比我小的个数」。

第三件事：r - mid - 1 是什么

r 从 mid + 1 出发，每从右半取走一个就 +1

已经取走的个数 = r - (mid + 1) = r - mid - 1

当左半的 helper[l] 终于被放下时，说明这些已取走的右半元素全都比它小（比它小才会先出队），而且原位置全在它右边（不变式）。

两个条件同时成立 → 它们正是 helper[l] 要数的人 → countArray[helper[l]] += (r - mid - 1)。

用 += 不是 =：同一个元素会在 log n 层 归并里各被结算一次，每层数的是不同批人，要累加。

第四件事：while (l <= mid)——右半剩下的不用管

标准归并会用 while (l <= mid || r <= right) 把两边都倒空。这里只写了左半，看着像 bug，其实是个巧妙的省略：

每写一格，cur 和 (l 或 r) 同时前进一格
   ⟹  cur = l + r - mid - 1   恒成立

左半用完时 l = mid + 1
   ⟹  cur = (mid+1) + r - mid - 1 = r

也就是说：剩下要填的位置 [cur, right]
         正好就是 helper 里没取的 [r, right]
而 helper 是 indexArray 的拷贝，且 cur <= r 保证这段从没被覆盖过
   ⟹  它们【已经在正确的位置上了】，一个字都不用写

而且它们也不需要计数——它们是右半的人，右边比它们小的，早在更深层的递归里数完了。

动图里每次 merge 结束都会把这段标成虚线，写着「原地不动」。

第五件事：谁在数、数谁

只有【左半】的元素会被计数
右半的元素在这一层一分不加

因为：右边比我小的人，只可能在我右边
      对左半的人来说，右半就是"我右边"
      对右半的人来说，同层的右半是"我左边"，不算

切到「全递增」那组：右半永远不会先出队，r - mid - 1 恒为 0，countArray 全程是 0。

切到「全递减」那组：右半每次都先出队，每个左半元素被放下时都能吃到满额。

复杂度

Time  O(n log n)   就是归并排序，计数是顺手的 O(1)
Space O(n)         helper + indexArray + countArray

暴力：对每个 i 扫右边一遍 → O(n²)
这题明确要求 O(n log n)，所以暴力过不了
